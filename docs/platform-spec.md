# Platform Specification — Eldercare Coordination Platform

Status: Draft for build · Companion docs: `adr.md` (decisions/rationale), `business.md` (process & philosophy)
Audience: development agents. Normative language: MUST / MUST NOT / SHOULD.

---

## 1. System overview

```
┌─────────────┐   sync (HTTPS)   ┌──────────────────────┐
│ Flutter app  │◄────────────────►│  Go monolith (single │
│  primaries:  │                  │  binary)             │
│  local-first │   REST/JSON      │  ┌────────────────┐  │
│  SQLite      │◄────────────────►│  │ modules:       │  │──► Postgres 16
├─────────────┤                  │  │ identity       │  │    (primary +
│ Flutter app  │   REST only,     │  │ circle         │  │    streaming
│  extended:   │   no replica     │  │ record         │  │    replica)
│  cloud-only  │                  │  │ incident       │  │
└─────────────┘                  │  │ feed           │  │──► KMS (DEK wrap)
┌─────────────┐   SSR + REST     │  │ sync           │  │
│ SvelteKit    │◄────────────────►│  │ enclave        │  │──► Object store
│  web client  │                  │  │ notify         │  │    (documents,
└─────────────┘                  │  │ audit          │  │    v1+)
                                  │  └────────────────┘  │
                                  └──────────────────────┘
```

- One Go binary. One repo. `go test ./...` runs everything.
- Server is **not** in the read path for crisis mode. Primaries' devices hold a full tier 1–3 replica; enclave (tier 4) data is device-resident only via explicit provisioning.
- Extended-family clients have no replica and no sync code path.

## 2. Repository layout

```
/cmd/server/            main.go — wires modules, serves HTTP
/internal/identity/     persons, auth, devices, sessions
/internal/circle/       care circles, memberships, roles, invitations
/internal/record/       tier 1–3 structured records (contacts, insurance, meds…)
/internal/incident/     incident log, check-ins (append-only)
/internal/feed/         posts, comments (tier 1–2)
/internal/sync/         changelog, push/pull endpoints, HLC
/internal/enclave/      tier-4 store. SEALED MODULE — see §9
/internal/notify/       fan-out: push, email
/internal/audit/        immutable read/write audit trail
/internal/platform/     db pool, KMS client, config, middleware
/migrations/            sql-migrate / goose, numbered, forward-only
/gen/                   sqlc output. NEVER hand-edited
/clients/app/           Flutter (two entrypoints: primary, extended)
/clients/web/           SvelteKit
```

Module rules (enforced, not advisory):
- A module's tables are accessed **only** by that module's queries. Cross-module access goes through the module's Go API. Enforce with `internal/` visibility + a CI check that greps `gen/` query files for out-of-module table names.
- `enclave` exposes exactly: `Put`, `Get`, `Delete`, `Provision`, `Revoke`, `ListProvisionedDevices`. Nothing else. No other module imports its storage layer.
- All row types generated by sqlc from `/migrations`. No hand-written structs mirroring tables.

## 3. Core schema (tiers 1–3; enclave schema in §9)

```sql
-- people ------------------------------------------------------------
CREATE TABLE person (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  display_name  text NOT NULL,
  email         citext UNIQUE,
  phone         text,
  created_at    timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE device (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  person_id     uuid NOT NULL REFERENCES person(id),
  platform      text NOT NULL CHECK (platform IN ('ios','android','web')),
  push_token    text,
  sync_cursor   text,                 -- HLC of last acked pull; NULL = never synced
  wipe_pending  boolean NOT NULL DEFAULT false,
  created_at    timestamptz NOT NULL DEFAULT now(),
  last_seen_at  timestamptz
);

-- circles -----------------------------------------------------------
CREATE TABLE care_circle (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  elder_id      uuid NOT NULL REFERENCES person(id),
  key_epoch     integer NOT NULL DEFAULT 1,   -- bumped on revocation (§8)
  elder_status  text NOT NULL DEFAULT 'living'
                CHECK (elder_status IN ('living','deceased')),
  created_at    timestamptz NOT NULL DEFAULT now()
);

CREATE TYPE circle_role AS ENUM ('primary','extended','elder');

CREATE TABLE circle_membership (
  circle_id     uuid NOT NULL REFERENCES care_circle(id),
  person_id     uuid NOT NULL REFERENCES person(id),
  role          circle_role NOT NULL,
  is_owner      boolean NOT NULL DEFAULT false,      -- role attribute, ADR-003
  can_write     boolean NOT NULL DEFAULT true,       -- elder write-degradation
  max_tier      smallint NOT NULL DEFAULT 2 CHECK (max_tier BETWEEN 1 AND 4),
  revoked_at    timestamptz,                          -- soft revoke; drives RLS
  created_at    timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (circle_id, person_id)
);
-- role defaults: primary → max_tier 4; extended → max_tier 1 (or 2);
-- elder → max_tier 3, can view own incident log always (RLS carve-out §5)

CREATE TABLE executor_designation (          -- named-only, ADR-010
  circle_id     uuid PRIMARY KEY REFERENCES care_circle(id),
  person_id     uuid REFERENCES person(id),  -- nullable: may be non-user
  free_text     text,                         -- "Susan Miller, eldest daughter"
  updated_by    uuid NOT NULL REFERENCES person(id),
  updated_at    timestamptz NOT NULL DEFAULT now()
);
-- every INSERT/UPDATE here MUST also write an incident-log entry (trigger)

-- tier 1–3 records ----------------------------------------------------
CREATE TABLE care_record (
  id            uuid PRIMARY KEY,             -- client-generated (sync)
  circle_id     uuid NOT NULL REFERENCES care_circle(id),
  tier          smallint NOT NULL CHECK (tier BETWEEN 1 AND 3),  -- tier 4 NEVER here
  kind          text NOT NULL,   -- 'physician','insurance','medication',
                                 -- 'allergy','pharmacy','appointment','poa_pointer'…
  fields        jsonb NOT NULL,  -- per-field LWW map: {name: {v, hlc, by}}
  deleted       boolean NOT NULL DEFAULT false,
  recorded_hlc  text NOT NULL,   -- HLC of last mutation
  updated_at    timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON care_record (circle_id, tier, kind) WHERE NOT deleted;

-- incident log (append-only) -----------------------------------------
CREATE TABLE incident (
  id            uuid PRIMARY KEY,             -- client-generated
  circle_id     uuid NOT NULL REFERENCES care_circle(id),
  kind          text NOT NULL,   -- 'emergency','fall','er_visit','checkin',
                                 -- 'checkin_missed','executor_change','access_change'
  severity      smallint,
  occurred_at   timestamptz,     -- user-asserted, editable via amendment rows only
  recorded_hlc  text NOT NULL,   -- device HLC, immutable
  recorded_at   timestamptz NOT NULL DEFAULT now(),  -- server receipt, immutable
  author_id     uuid NOT NULL REFERENCES person(id),
  body          jsonb NOT NULL,
  amends        uuid REFERENCES incident(id)  -- corrections are new rows
);
-- NO UPDATE, NO DELETE. Enforce: REVOKE UPDATE, DELETE ON incident FROM app_role;

-- feed ----------------------------------------------------------------
CREATE TABLE post (
  id            uuid PRIMARY KEY,
  circle_id     uuid NOT NULL REFERENCES care_circle(id),
  tier          smallint NOT NULL DEFAULT 1 CHECK (tier IN (1,2)),
  author_id     uuid NOT NULL REFERENCES person(id),
  body          text,
  media_ref     text,
  recorded_hlc  text NOT NULL,
  created_at    timestamptz NOT NULL DEFAULT now(),
  deleted       boolean NOT NULL DEFAULT false
);

-- audit (append-only, ADR-007) ----------------------------------------
CREATE TABLE audit_event (
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  at            timestamptz NOT NULL DEFAULT now(),
  person_id     uuid NOT NULL,
  device_id     uuid,
  circle_id     uuid NOT NULL,
  action        text NOT NULL,   -- 'read','reveal','write','provision','revoke','wipe_ack'
  object_type   text NOT NULL,   -- 'care_record','enclave_item','incident',…
  object_id     uuid,
  tier          smallint
);
-- REVOKE UPDATE, DELETE. Tier 3–4 reads and all reveals MUST land here.
-- Primaries can view their circle's audit trail (this is the abuse tripwire).
```

Forbidden schema patterns (CI-checked):
- No `is_sensitive` boolean anywhere. Sensitivity is tier + enclave placement.
- No `max_elders`-style limits.
- No aggregate views/materialized views computing per-person historical counts on `incident` or task tables.

## 4. Identity & auth

- Auth: email or phone + OTP for account creation; session tokens (opaque, server-side) thereafter. No passwords in MVP.
- Elder onboarding: primary generates a one-time enrollment code rendered as QR + 6-digit PIN, TTL 72h, single-use. Redemption creates `person` (if new) + `circle_membership(role='elder')` and binds the device.
- Device binding: every mobile session is tied to a `device` row. Required for sync cursors, provisioning enumeration, and wipe.
- Sensitive-tier access on device: standard OS auth prompt (`LocalAuthentication` / `BiometricPrompt`) with device-credential fallback. Keystore-wrapped keys require unlock. No app-level PIN.

## 5. Authorization — Postgres RLS

All circle-scoped tables carry RLS. App connects as `app_role` (not owner, not superuser — RLS is bypassed for table owners). Per-request:

```sql
SET LOCAL app.person_id = '<uuid>';
```

Canonical policy shape:

```sql
ALTER TABLE care_record ENABLE ROW LEVEL SECURITY;

CREATE POLICY circle_read ON care_record FOR SELECT USING (
  EXISTS (
    SELECT 1 FROM circle_membership m
    WHERE m.circle_id = care_record.circle_id
      AND m.person_id = current_setting('app.person_id')::uuid
      AND m.revoked_at IS NULL
      AND m.max_tier >= care_record.tier
  )
);

CREATE POLICY circle_write ON care_record FOR INSERT WITH CHECK (
  EXISTS (
    SELECT 1 FROM circle_membership m
    WHERE m.circle_id = care_record.circle_id
      AND m.person_id = current_setting('app.person_id')::uuid
      AND m.revoked_at IS NULL
      AND m.can_write
      AND m.max_tier >= care_record.tier
  )
);
```

Carve-outs (separate policies):
- Elder always SELECTs `incident` rows and `care_record` rows of their own circle regardless of `max_tier`/`can_write` (ADR-001 transparency invariant).
- `audit_event`: SELECT for primaries of the circle; INSERT via app only.
- Revoking a `primary`: guarded in the `circle` module — requires a second non-revoked primary to exist and to approve (two-primary rule; policy flag until ADR-003 is finalized, but the code path MUST exist).

Rules for agents:
- MUST NOT add `WHERE circle_id = ?` as the *only* isolation mechanism; RLS is the boundary, application filters are optimization.
- MUST NOT create SECURITY DEFINER functions touching circle-scoped tables without explicit human review.
- MUST NOT connect as a role that owns the tables.

## 6. Sync protocol (primaries only)

Transport: HTTPS JSON. Two endpoints. Cursor-based. Client-generated UUIDv7 ids.

### 6.1 Hybrid logical clock
- HLC string, lexically sortable: `0x<48-bit physical ms><16-bit counter>-<device_id_short>`.
- Every mutation on device stamps `recorded_hlc`. Server maintains its own HLC and merges on receipt. Wall-clock skew > 5 min between device and server → server clamps and flags the device (surface in diagnostics, don't reject).

### 6.2 Push
```
POST /v1/sync/push
{ device_id, circle_id, ops: [
    { table: "incident"|"care_record"|"post",
      op: "insert"|"field_set"|"tombstone",
      id, hlc, payload } ] }
→ { accepted: [ids], rejected: [{id, reason}], server_hlc }
```
- `incident`: `insert` only (append-only; corrections are new rows with `amends`).
- `care_record.field_set`: per-field LWW. Server merges field-wise: apply iff incoming field HLC > stored field HLC. No whole-record clobber.
- All ops pass through RLS under the pushing user's identity. A rejected op (tier too high, revoked membership) returns `reason: "denied"` and the client discards local state for it.

### 6.3 Pull
```
POST /v1/sync/pull
{ device_id, circle_ids: [...], cursor }        -- cursor = last acked server HLC
→ { changes: [...], next_cursor, control: { wipe: bool, key_epoch: {circle_id: n} } }
```
- Changes are RLS-filtered **and tier-filtered to ≤3**. Tier-4 never appears in a sync response under any circumstance (belt: enclave data isn't in synced tables; suspenders: sync module hard-asserts `tier <= 3` on every outbound row and panics otherwise — this assert is load-bearing, do not remove).
- `control.wipe = true` → client drops local DB, acks with `POST /v1/sync/wipe-ack`, server clears `wipe_pending`, audit-logs `wipe_ack`.
- `key_epoch` mismatch → client re-requests circle key material before applying changes (§8).

### 6.4 Client storage (Flutter, primary build)
- SQLite via Drift. Mirror tables for `care_record`, `incident`, `post` + `pending_ops` outbox + `field_hlc` sidecar for LWW.
- Outbox drains FIFO on connectivity; pull runs after every successful push and on foreground + FCM/APNs silent-push nudge.
- Crisis screen reads only local tables. MUST render < 1s from cold launch on a mid-tier device. No network on that path; sync runs after render, in background.

## 7. Crisis mode contract

- Entry: one tap from app cold launch (primary build). Elder-selector only if the user is primary on >1 circle.
- Content: tier-3 payload — meds, allergies, conditions, DNR/POA pointers, physicians, insurance card fields — plus provisioned enclave items if the user unlocks (§9).
- Offline: fully functional with radio off. CI includes an integration test that renders crisis mode with network mocked dead.
- Broadcast: one action posts a tier-2 incident + fans out push/SMS/email to the circle ("Dad is at St. Joseph ER, more soon"). Queued locally if offline, sent on reconnect.
- Every crisis-mode open writes a local audit event (synced later): this is both the usage metric and the incident-correlation signal.

## 8. Revocation & key epochs

- Circle content keys are per-epoch. Revoking any member bumps `care_circle.key_epoch`; current members' devices fetch the new epoch key on next pull; the revoked device is not issued it.
- Revocation sequence (server): set `membership.revoked_at` → bump epoch → set `wipe_pending` on the member's devices → notify remaining primaries.
- Wipe scope: app-sandbox data only (local DB, caches, provisioned enclave store). MUST NOT touch anything outside the sandbox.
- Residual-risk copy (snapshot retention by uncooperative devices) lives in the privacy policy — see `business.md`. Client and marketing copy MUST NOT describe wipe as guaranteed.

## 9. Enclave module (tier 4) — sealed

Internals are finalized in a dedicated security session. Until then, agents implement **only** this contract and MUST NOT extend it.

```sql
CREATE SCHEMA enclave;   -- separate schema; separate migration dir gate

CREATE TABLE enclave.item (
  id            uuid PRIMARY KEY,
  circle_id     uuid NOT NULL,           -- no FK into public schema by design
  kind          text NOT NULL,  -- 'will_pointer','insurance_policy','funeral_plan',
                                -- 'organ_donation','ssn_last4','attorney','document'
  ciphertext    bytea NOT NULL, -- AES-256-GCM, per-circle DEK (KMS-wrapped, per epoch)
  created_by    uuid NOT NULL,
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE enclave.provision (
  item_scope    text NOT NULL DEFAULT 'circle',  -- v1: whole-circle provisioning
  circle_id     uuid NOT NULL,
  device_id     uuid NOT NULL,
  person_id     uuid NOT NULL,
  granted_by    uuid NOT NULL,
  key_epoch     integer NOT NULL,
  created_at    timestamptz NOT NULL DEFAULT now(),
  revoked_at    timestamptz,
  PRIMARY KEY (circle_id, device_id)
);
```

Hard rules:
1. `enclave.*` tables are readable/writable only by the `enclave` Go module. No other sqlc query file references schema `enclave`. CI-enforced.
2. Plaintext values never leave the module except through `Get` (audited) and the provisioning payload (audited). Never in search indexes, notifications, telemetry, feed, or sync responses.
3. Device residency only through `POST /v1/enclave/provision` (primary-initiated, per-device, consent copy shown). Provisioned devices are enumerable: `GET /v1/enclave/devices?circle_id=…`.
4. On-device: separate SQLCipher store (not the main replica DB), DEK wrapped by hardware keystore, unlock via OS auth prompt. Main-replica file contains zero enclave plaintext.
5. Provisioned copies are fully offline-readable after unlock. No network in the read path.
6. Every `Get`/reveal → `audit_event(action='reveal', tier=4)`.
7. SSN: store last-4 as its own `kind`; full SSN storage is out of scope until the security session says otherwise.

## 10. Notifications

- Channels: APNs/FCM push, email (SES or similar), SMS for crisis broadcast only (Twilio).
- Notification bodies are tier-0: "New update on Mom" / "Emergency alert — open app". Never names of conditions, meds, or enclave-derived values. Content renders after auth, in-app.
- Silent push nudges sync; visible push for feed/incidents per user prefs; crisis broadcast overrides prefs.

## 11. Telemetry, logging, environments

- Structured logs (slog). A redaction layer at the emitter strips: person names, email, phone, all `fields` payload values, anything from the enclave module (which logs only ids + actions). Sinks receive post-redaction records only.
- Crash reporting: same rule. If it can't be guaranteed, crash reports carry no request payloads.
- Metrics for grant reporting come from `incident` + `audit_event` aggregates computed server-side, **never per-person historical totals** (per-kind, per-circle, per-period only).
- Environments: `dev`, `staging`, `prod`. Non-prod seeds from `/seed/synthetic/` generators only. No credential path from non-prod to prod DB. CI blocks any fixture file containing a real-looking SSN/policy-number pattern.

## 12. Web client (SvelteKit)

- SSR, session-cookie auth against the same monolith. No offline, no replica, no service-worker caching of tier ≥3 responses (`Cache-Control: no-store`).
- Surfaces: full record entry (desktop data-entry is the fast path for onboarding), feed, incident log, audit view for primaries, admin scaffolding for future caseworker role (nav stub only in MVP).
- Tier 3–4 views require step-up: re-auth (OTP) within the last 10 minutes; tier-4 reveals audited identically to mobile.

## 13. Flutter builds

- Two entrypoints, one codebase: `main_primary.dart` (replica + sync + crisis + enclave client) and `main_extended.dart` (REST-only; sync/enclave/crisis libraries not linked — verify via `--dart-define` + tree-shaking check in CI that the extended artifact contains no Drift schema symbols).
- Elder mode is the primary build with `role=elder` server-driven UI: check-in button (one tap, huge target), today's appointments, own record view. No gestures required anywhere in elder-facing screens; min touch target 48dp; font scale respected to 200%.

## 14. Testing gates (CI)

1. `go test ./...` — unit + module boundary tests.
2. RLS suite: for each table × role × tier, assert visible/invisible rows against a seeded matrix. Runs against real Postgres (testcontainers).
3. Sync property tests: two simulated devices, randomized op interleavings, converge to identical state; append-only tables converge by union; LWW respects HLC order.
4. Crisis offline test: network-dead render < 1s with seeded replica.
5. Static gates: no cross-module table access in `gen/`; no `enclave.` outside `internal/enclave`; no `is_sensitive`; no per-person aggregate SQL on `incident`; tier ≤ 3 assert present in sync pull path.
6. Extended-build symbol check (§13).

## 15. Build order (PoC, 3–4 months)

1. **M1 — spine:** migrations, identity, circle, RLS + RLS test matrix, sqlc pipeline, SvelteKit auth + record CRUD.
2. **M2 — sync:** HLC, push/pull, Drift replica, outbox; two-device convergence tests.
3. **M3 — crisis:** tier-3 record kinds, crisis screen, offline gate, broadcast fan-out, incident log + check-in.
4. **M4 — enclave v1:** schema + module contract, pointer kinds, provisioning, on-device SQLCipher store, audit/reveal, OS-auth unlock.
5. **M5 — hardening:** revocation/epoch/wipe flow, elder onboarding QR/PIN, elder mode UI, telemetry redaction audit, seed-data generators, grant-metric aggregates.

Feed for extended family is M5+ / v1 — it is deliberately last (see `business.md` §wedge).
